# Vibration AI - Model Diagnostic Report

This document outlines the investigation into why the vibration ML classification model defaults to "Normal/AC" in production and fails to correctly identify or explain predictions for other fault classes.

*Note: The original prompt template asked about "unbalance, misalignment, bearing defect, looseness" and "SHAP/LIME" explainability, which are not present in this specific repository. This diagnostic is based strictly on the actual code, classes, and data present in the `vibration_ai` project.*

---

## 1. Dataset & Class Distribution
An analysis was run on the extracted `features_y.npy` and the `evaluation_report.txt` generated by the training script.

* **Distribution**: The dataset currently contains **185 total samples**. The dataset is well-balanced across the 5 classes:
  * Class 0: Normal/AC
  * Class 1: Footsteps
  * Class 2: Sabotage/Maintenance
  * Class 3: Vehicle
  * Class 4: Earthquake
* **Conclusion**: **Class imbalance is NOT the root cause.** The model has plenty of balanced examples for all classes during training.

---

## 2. Feature Extraction Issues
The feature extractor (`1_feature_extractor.py`) computes 14 statistical features (ZCR, mean, MAD, skewness, STD, kurtosis, crest factor, min, max, range, median, IQR, RMS, energy).

While these are generally effective features, there is a **major flaw in how JSON sensor data is preprocessed**:

```python
# In 1_feature_extractor.py
sig_min = np.min(sig)
sig_max = np.max(sig)
if sig_max > sig_min:
    sig = 2.0 * (sig - sig_min) / (sig_max - sig_min) - 1.0
```

**The Problem:** Min-Max scaling to `[-1.0, 1.0]` is being applied on a *per-sample* (per-window) basis. This completely destroys absolute amplitude information! A massive earthquake and a tiny AC vibration will both be scaled to have the exact same peak amplitude of `1.0`. Features like `min_val`, `max_val`, and `range_val` will be mathematically identical (`-1.0`, `1.0`, `2.0`) for every single JSON sample regardless of the class.

---

## 3. Model Training vs. Deployment Mismatch (The Primary Bug)
When comparing the training script against the deployment script, we identified the **#1 reason why the model is failing in production**:

* **In Training (`2_model_trainer.py`)**: The `RandomForestClassifier` is trained directly on raw, unscaled features. No scaler is fitted, and no `scaler.pkl` is saved. The model learns the raw ranges of the 14 features.
* **In Deployment (`bridge/mqtt_to_supabase.py`)**: 
  ```python
  # SCALER_PATH points to an old scaler.pkl
  ai_scaler = joblib.load(SCALER_PATH) 
  
  # ... later in the code ...
  features = extract_features_from_signal(signal)
  features_scaled = ai_scaler.transform([features]) # <-- MASSIVE BUG
  probs = ai_model.predict_proba(features_scaled)[0]
  ```

**The Result:** The bridge script is loading an old, stale `scaler.pkl` (left over from an older version of the project) and applying it to live features. Because the live data is being scaled before being fed into a model that was trained on *unscaled* data, the input is entirely out-of-distribution. This causes the Random Forest to fall back to random/majority predictions (usually class 0). 

Furthermore, the deployment script has a hardcoded bypass (`if range_g < 0.02: ai_label = "Normal/AC"`), which forces any low-vibration states directly to AC.

---

## 4. Confusion Matrix & Metrics
A review of the `evaluation_report.txt` on the 20% holdout test set (where the stale scaler bug doesn't exist) shows that the model architecture itself is sound.

* **Overall Accuracy**: 89.19%
* **Normal AC (Class 0)**: 100% Recall
* **Footsteps (Class 1)**: 100% Recall
* **Sabotage (Class 2)**: 78% Recall
* **Vehicle (Class 3)**: 78% Recall

**Conclusion:** The model works perfectly fine in offline evaluation. It only fails in deployment due to the scaler mismatch.

---

## 5. Explainability (SHAP/LIME)
A search across the entire project structure reveals that there are **no SHAP, LIME, or feature importance scripts implemented anywhere in this repository**. 

The "metadata" output only contains the `ai_label` and `ai_confidence` (the max probability from the Random Forest). If explainability (feature importance/SHAP) is desired, new scripts must be written to analyze the Random Forest.

---

## 6. Suggested Code Changes (How to Fix)

To get the model predicting correctly in production, these fixes should be applied:

### Change 1: Fix `bridge/mqtt_to_supabase.py` (Critical)
Remove the scaler transformation so the live data matches the training data format.

```diff
- SCALER_PATH = os.path.join(AI_MODELS_DIR, "scaler.pkl")
- ai_scaler = joblib.load(SCALER_PATH)
...
- features_scaled = ai_scaler.transform([features])
- probs = ai_model.predict_proba(features_scaled)[0]
- pred_class = int(ai_model.predict(features_scaled)[0])
+ features_scaled = [features]  # Pass raw features to match training
+ probs = ai_model.predict_proba(features_scaled)[0]
+ pred_class = int(ai_model.predict(features_scaled)[0])
```

### Change 2: Fix Amplitude Destruction in `1_feature_extractor.py` (Important)
Instead of dynamically scaling every JSON sample to `[-1, 1]`, scale it based on the absolute sensor capability (e.g., if the ESP32 accelerometer is set to ±2g or ±4g, divide by that constant) so that magnitude is preserved across different classes.

```diff
- sig_min = np.min(sig)
- sig_max = np.max(sig)
- if sig_max > sig_min:
-     sig = 2.0 * (sig - sig_min) / (sig_max - sig_min) - 1.0
+ # Scale by absolute max G-force (e.g., ±2g range) to preserve relative magnitude
+ sig = np.clip(sig, -2.0, 2.0) / 2.0 
```
